# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Automatic dart scoring on a Raspberry Pi 4 (64-bit Raspberry Pi OS) using three InnoMaker 720p USB cameras mounted on a ring around the board, plus OpenCV 4.10 (system Python 3, no virtualenv or dependency manifest). Planned pipeline: camera capture → calibration → dart detection → score calculation → game logic → web scoreboard. Calibration (manual point picking) and a first version of dart detection exist; detection still needs tuning on real throws.

The development environment (devices, Tailscale network, tmux session `dart`, GitHub over SSH, how the scoreboard is reached) is described in Swedish in [`ARKITEKTUR.md`](ARKITEKTUR.md). Keep it up to date when that setup changes.

## Commands

All commands run from the repo root (scripts import the `dart_scoring` package relatively).

- `python3 main.py` — runs `calculate_score` on a few hard-coded sample points (no hardware needed).
- `python3 test_cameras.py` — opens all three cameras via `CameraManager`, discards 15 frames for auto-exposure, writes `images/camera_{1,2,3}.jpg`. Requires the cameras to be connected.
- `python3 web_server.py [--port 8000]` — web scoreboard on http://<pi-ip>:8000/ (stdlib only, no Flask). Darts can be entered manually in the page until detection exists. On the Pi it runs as the systemd **user** service `dart-scoreboard` (unit in `systemd/`, linger enabled so it starts at boot; no sudo available). After changing server code: `systemctl --user restart dart-scoreboard`. Logs: `logs/web_server.log` (rotated at 1 MB, 3 backups; the user journal is not persisted on this Pi, so `journalctl --user` shows nothing). Don't also start `web_server.py` by hand on port 8000 — it will conflict.
- `python3 calibrate.py [--port 8001]` — calibration tool on http://<pi-ip>:8001/. Captures a frame from every camera (button to recapture). The "Alla" tab shows all three side by side, with an optional live MJPEG view (`/stream/<id>.mjpg`, ~9 fps, 640×360) for aiming the cameras; a background thread (`LiveCameras`) keeps the cameras open while anyone streams or captures and closes them 3 s after. The user clicks labelled reference points in each image and the page draws the fitted board on top. Saves to `calibration.json` in the repo root (gitignored; redo after moving a camera). It holds all cameras while capturing, so don't run it alongside other camera scripts.
- `python3 detect.py [--dry-run] [--save]` — dart detection. The board must be empty when it starts. Sends each dart to the scoreboard (`--server`, default http://localhost:8000) unless `--dry-run`; `--save` writes before/after/debug images and `event.json` per event to `captures/` (gitignored) for tuning. Logs to `logs/detect.log`. Holds all cameras, like `calibrate.py`. With `--save` each dart is sent with its capture folder name, so a correction on the scoreboard writes `truth.json` (the right value) into that folder.
- `python3 evaluate_captures.py [--all]` — replays the current detection code on every saved dart that has a `truth.json` and reports how many it gets right (and what the detector said live). Use it to check a detection change against all corrected darts instead of a single throw; replays run on the saved JPEGs, so they can differ slightly from live.
- `python3 test_camera.py` — single-camera smoke test on `/dev/video0`, writes `camera_test.jpg`.

Unit tests (pytest, install with `sudo apt install python3-pytest`):

- `python3 -m pytest` — runs everything in `tests/`.
- `python3 -m pytest tests/test_scoring.py::test_cardinal_directions` — a single test.

`pyproject.toml` restricts collection to `tests/` and puts the repo root on `sys.path`. The top-level `test_camera.py` / `test_cameras.py` are manual hardware scripts that open cameras at import time — never let pytest collect them.

## Architecture

- **`dart_scoring/camera.py`** — `CameraManager` opens cameras by stable `/dev/v4l/by-path/...` names (`CAMERA_PATHS`), so camera IDs 1–3 are tied to **physical USB ports** (ports 2–4 of the USB hub in the Pi's USB 2.0 port 1.1, i.e. 1.1.2, 1.1.3, 1.1.4; hub port 1 is unused), not `/dev/videoN` enumeration order. Moving a camera to another port changes its ID. Cameras are configured for MJPG 1280×720 @ 30 fps with a fixed exposure (`EXPOSURE`, 20 ms, gain 0) so brightness stays stable between frames and auto exposure cannot drop the frame rate; white balance stays automatic because the manual colour temperature cannot remove the LED ring's green tint. `capture()` calls `grab()` on every camera first and only then `retrieve()`, to keep the three frames as close to simultaneous as possible. Keep that two-phase pattern when changing capture code.
- **`dart_scoring/scoring.py`** — `calculate_score(x, y)` works in **normalized board coordinates**: origin at the bull, radius 1.0 = outer edge of the double ring (170 mm), and **negative y points up** toward the 20 (image-style coordinates). Ring boundaries are standard board dimensions in mm divided by 170. `SEGMENTS` lists numbers clockwise starting at 20. Detection and calibration are expected to produce points in this coordinate system (e.g. via homography from each camera view).
- **`dart_scoring/calibration.py`** — per camera, a model from image pixels to normalized board coordinates, fitted from reference points: a ring edge (`RINGS`) crossed with a segment-boundary wire (boundary `i` = wire between `SEGMENTS[i]` and `SEGMENTS[i+1]`, so 0 is 20/1), or the bull center. With at least `MIN_DISTORTION_POINTS` (12) points, `fit()` also estimates radial lens distortion (k1, k2) with single-view `cv2.calibrateCamera` (free principal point, fixed aspect ratio) and fits the homography on undistorted points; the wide-angle lenses (k1 ≈ -0.47) put a plain homography tens of pixels off near the image edges. With fewer points it falls back to a plain pixel homography. A camera entry in `calibration.json` holds `camera_matrix`, `dist_coeffs` and `homography`; entries without the first two are treated as identity/no distortion, so old files still load. Functions take the whole entry: `image_to_board(entry, u, v)` is what detection should use on the dart tip pixel. `find_suspects()` flags points (leave-one-out, then rechecked against a fit without all candidates) that are probably misclicked or mislabelled and suggests the label the model puts closest. `calibration_web.py` + `static/calibrate.html` are the point-picking UI; it shows suspects in red with a one-click label fix.
- **`dart_scoring/detection.py`** — `Detector.feed(frames, now)` is a state machine: a motion check on 320×180 greyscale images, and when the view has been still for `STILL_FRAMES` after motion, `evaluate()` compares full-resolution frames with the reference taken after the last event, in colour (largest change of any channel): the steel point over the green ring is as bright as the green and vanishes in grey. The changed pixels in each camera are fitted with a line (`find_dart`); the lower end of the blob is the visible tip, and `extend_tip` follows the line a little further (plain colour difference, no shake tolerance) because the tolerance drops a thin point where it crosses a wire or colour edge. Each camera's line is mapped onto the board plane, where it passes through the real tip, and `locate()` intersects the lines (all three, else the best pair, else the median of the visible tips), so a hidden or thin point doesn't matter. Each visible tip also pulls the intersection a little, weighted by its camera's mm per pixel there (`TIP_REFERENCE_MM_PER_PX`), so the camera closest to the dart decides where along the lines it sits. When only two lines meet at a shallow angle (< `SHARP_TIP_ANGLE`) one camera sees `SHARP_TIP_RATIO` times sharper and the intersection lands behind its visible tip (shaft side), that tip is used instead; beyond the tip is kept, since the thin steel point often goes unseen against the board. `change_mask` tolerates a shift of `SHIFT_PX` (cameras shake on impact). Takeout = frames look like the stored empty board again; a dart pulled out = less change against the empty board than before. Runs at ~8 checks/s on the Pi (MJPG decode of three frames is ~38 ms). Tests in `tests/test_detection.py` use three synthetic wide-angle cameras and rendered darts.
- **`dart_scoring/game.py`** — X01 rules (`Game`): 3 darts per turn, bust reverts to the score at turn start, optional double out (bullseye counts as a double). A finished turn stays visible until the next throw or `next_player()`; `takeout()` fills a started, unfinished turn with misses; `correct(index, ...)` changes a dart of the turn on display (also a finished turn, until the next throw) and recounts the turn; `undo()` restores deep-copied snapshots. A `Dart` carries the detector's `capture` folder name and a `corrected` flag.
- **`dart_scoring/web.py`** — `ThreadingHTTPServer` holding one shared `Game` behind a lock. JSON API: `GET /api/state`, `POST /api/new-game`, `/api/throw` (`{segment, multiplier}` or normalized `{x, y}` via `scoring.classify`), `/api/takeout` (darts pulled: fill the turn up with misses, for darts that missed the board and were never detected), `/api/correct` (`{index, segment, multiplier}`; for a detected dart also writes `captures/<capture>/truth.json`, keeping the first detected label when corrected twice), `/api/next`, `/api/undo`. In the page, clicking a dart of the turn puts the number pad in correction mode. The page (`dart_scoring/static/index.html`, plain HTML/JS) polls `/api/state` every second, so several screens stay in sync. `detect.py` feeds darts in via `/api/throw` with `{x, y, capture}` and posts `/api/takeout` on a takeout.
